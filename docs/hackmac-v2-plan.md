# HackMac v2 기획

사용자가 하고 싶은 것을 말하면, 이미 쓰고 있는 Claude Code나 Codex가 그걸 맥 앱으로 만들어 주고, 사용자는 켜기만 하는 플랫폼. 만든 앱은 파일 하나로 내보내 다른 사람의 HackMac에 바로 설치할 수 있다.

## 1. 무엇이 바뀌나

| | v1 (지금) | v2 |
|---|---|---|
| 서비스/앱을 만드는 사람 | 우리(개발자)가 번들에 넣음 | 사용자가 채팅으로 만듦 |
| 실행 단위 | 단축키 하나 = 스크립트 하나 | 앱 하나 = 패키지 하나(단축키·상주·스케줄 등 트리거 여럿) |
| 저장 위치 | 앱 번들 안 `resources/services`(읽기 전용, 시작 시 1회 스캔) | 사용자 데이터 폴더(만들자마자 목록에 나타남) |
| 공유 | 없음 | 파일 하나로 내보내기/설치하기 |

v1에서 그대로 이어지는 원칙:

- 사용자가 보는 화면은 팝업까지 전부 [design.md](design.md)의 디자인 시스템을 따른다. 앱이 사용자와 상호작용할 때는 osascript 다이얼로그가 아니라 HackMac 팝업 능력을 부른다.
- 앱은 판단 지점마다 stdout/stderr로 로그를 남기고, 실행기가 실행별 로그 파일에 담는다.

## 2. 사용자 여정

1. **dmg 더블클릭.** 사용자는 아무것도 몰라도 된다.
2. **준비.** 부족한 환경(claude/codex CLI 등)을 자동으로 검사하고 설치한다. **[결정]** 안내만 하지 않고 설치까지 한다.
3. **로그인.** Claude와 GPT 중 고르고, 공식 CLI의 로그인 흐름을 띄운다. **[결정]** 구독이 없는 사용자는 대상이 아니다.
4. **홈.** 설치된 앱 목록과 [앱 만들기] 버튼.
5. **앱 만들기.** 채팅 스레드가 열린다. 스레드는 계속 남고, 앱 하나와 짝이 된다. "이 앱 고쳐줘"는 그 스레드를 다시 여는 것이다([12절](#12-스레드--기억--레시피)).
6. **제작.** 요구 정리 → 가능성 평가 → 개발 → 자체 검증 → 사용자 확인 → 완료([7절](#7-제작-과정)). 진행 현황은 메뉴바와 HackMac 안에서 보인다([8절](#8-진행-현황-화면)).
7. **켜기.** 켜면 바로 동작한다. 백그라운드 앱도 된다.
8. **내보내기/설치하기.** 파일 하나로 빠지고, 받은 사람은 [앱 설치하기]에 올리면 바로 적용된다([9절](#9-앱-패키지와-이식성)). 앱 대신 **레시피**(프롬프트 하나)를 보내 받는 사람이 자기 환경에 맞게 다시 만들게 할 수도 있다([12.3](#123-레시피)).
9. **쓰는 동안.** HackMac이 앱 오류를 감시하다가 고칠 수 있는 것이면 스스로 수정본을 만들어 "적용할까요?"를 묻는다([11절](#11-로그와-자가-유지보수)).

## 3. 용어

- **앱**: 사용자가 만들고 켜고 공유하는 단위. 패키지 하나(폴더 하나).
- **모듈**: HackMac 플랫폼을 이루는 부품. 앱과 같은 모양(선언 + 코드 + 화면 조각)이다.
- **능력**: 앱이 요청할 수 있는 플랫폼 기능(팝업, 트레이, 알림, 단축키, 스케줄, AI 호출, 맥 헬퍼). 능력 하나가 모듈 하나다.
- **규격**: 모듈끼리, 앱과 능력끼리 주고받는 말의 모양(선언 · 봉투 · 권한 어휘). 정의만 있고 실행 코드는 없다.
- **엔진**: 사용자의 로컬 Claude Code 또는 Codex CLI.

## 4. 모듈 구조

### 4.1 원칙 [결정]

참고: collaboration-studio의 "스튜디오 구조: 여섯 모듈" 그림.

1. **모듈 = 폴더 하나.** 선언, 코드, 화면 조각이 같이 있다. 틀은 설치된 모듈의 선언만 읽어 화면을 켜므로, 폴더를 지우면 탭도 사라진다.
2. **모듈끼리는 규격의 봉투로만 말한다.** 다른 모듈의 내부 파일을 읽지 않는다.
3. **필수/선택을 선언한다.** 빠지면 무엇이 안 되는지 적는다.
4. **교체 길은 하나.** 시험 → 복구점 → 교체 → 재시험. 실패하면 되돌린다. 앱이 도는 중이면 교체하지 않고, 데이터는 지우지 않는다.
5. **생성된 앱도 같은 모양의 패키지다.** 제작 모듈이 만든 것과 사람이 만든 것이 구분되지 않는다.

모든 모듈은 언제든 독립적으로 삭제/교체/수정할 수 있어야 한다.

### 4.2 그림

```
        틀 (창·메뉴바·탭)  ← 설치된 모듈의 선언을 읽어 탭을 켠다
 ─────────────────────────────────────────────────────────
 시작   준비 ─▶ 계정
 만들기 대화 ─▶ 제작 ─▶ [앱 패키지]
 쓰기   보관소 ◀─ [앱 패키지] ◀─▶ 꾸러미(내보내기/설치)
        실행기 ─▶ 능력들(팝업·트레이·알림·단축키·스케줄·AI 호출·맥 헬퍼)
 ─────────────────────────────────────────────────────────
 규격: 선언 · 봉투 · 권한 어휘 (정의만)
 바닥(모듈 아님): macOS · 공식 CLI(claude/codex) · Electron
```

### 4.3 모듈 9개

| 모듈 | 맡는 일 | 빠지면 | v1에서 오는 코드 |
|---|---|---|---|
| 틀 | 창, 메뉴바, 탭. 모듈 선언을 읽어 화면 조각을 붙인다. 판단하지 않는다 | 필수 | `electron/main.ts`, `src/App.tsx` |
| 준비 | 첫 실행에서 빠진 환경을 검사하고 설치 | 필수(첫 실행) | 없음 |
| 계정 | Claude/GPT 선택, 공식 CLI 로그인·상태 확인, 계정 전환. 토큰은 읽지 않는다 | 필수 | 없음 |
| 대화 | 채팅 스레드 저장, 엔진 상주 프로세스. Claude와 Codex는 같은 인터페이스 뒤의 어댑터 | 제작 불가 | 없음 |
| 제작 | 맥 전문 에이전트의 지침·지식, 가능성 평가, 검증 루프, 재조사. 출력은 앱 패키지 | 제작 불가(설치된 앱은 돈다) | 없음 |
| 보관소 | 설치된 앱 목록, 선언 검증, 설치/삭제, 버전 | 필수 | `electron/services.ts`, `parser.ts`, `settings.ts` |
| 꾸러미 | 앱을 파일 하나로 묶기/풀기 | 공유만 안 됨 | 없음 |
| 실행기 | 켜기/끄기, 백그라운드 상주, 재시작, 실행 로그 | 필수 | `electron/runner.ts`, `exec-log.ts` |
| 능력들 | 앱이 요청하는 플랫폼 기능. 능력마다 독립 모듈 | 그 능력을 쓰는 앱만 "준비 중" | `popupServer.ts`, `popupWindow.ts`, `hotkeys.ts`, `trayStatus.ts` |

업데이트(`electron/updater.ts`)는 선택 모듈로 둔다.

### 4.4 앱이 쓸 수 있는 기능의 범위 [결정]

**생성된 앱은 HackMac이 제공하는 능력의 조합과 스크립트만 쓴다.** 앱이 자기 네이티브 코드를 가져오지 않는다.

- 이유 1: 사용자 맥에는 Xcode가 없어 Swift를 현장에서 컴파일할 수 없다.
- 이유 2: 사용자 맥에는 우리 서명 인증서가 없어, 에이전트가 만든 바이너리는 서명 없이 돌아야 한다.
- 이유 3: 다른 사람 맥에서 그대로 돌아야 한다([9절](#9-앱-패키지와-이식성)).

네이티브 기능은 우리가 미리 빌드하고 서명한 헬퍼를 능력 모듈로 번들한다. 새 능력이 필요하면 HackMac 업데이트로 추가한다. 능력 목록이 곧 앱의 한계다.

같은 이유로 **앱은 오픈소스 패키지를 동봉하지 않는다.** 오픈소스는 참고(방식을 빌려 스크립트로 다시 쓰기)만 허용하고, 라이브러리가 필요한 일은 우리가 능력으로 만든다([13절](#13-오픈소스)).

## 5. 프로세스와 실패 대비

### 5.1 백그라운드 방식 [결정: A]

- **A. HackMac 본체가 상주하고 앱은 그 자식으로 돈다. ← 채택.** 트레이, 단축키, 팝업이 모두 HackMac 프로세스 안의 기능이라, 이 능력을 쓰는 앱은 어차피 HackMac 없이 못 돈다. launchd가 HackMac 바이너리를 직접 띄우므로 권한 승인 창에도 HackMac으로 표시된다.
- B. 앱마다 launchd에 등록. 트레이·단축키·팝업을 못 쓰고, 권한 승인이 `osascript`/`zsh` 앞으로 떠 앱마다 따로 쌓인다(확인은 안 함). 채택 안 함.
- C. 앱마다 독립 `.app`. 사용자 맥에서 서명할 수 없어 Gatekeeper가 막는다. 불가.

### 5.2 프로세스 분리 [결정]

```
launchd (macOS가 살려 둠)
 ├─ 실행 서버   창 없음. 메뉴바·단축키·팝업·트레이 + 앱 자식 프로세스들
 └─ 엔진 지기   claude/codex 프로세스를 들고 있음
작업실         스토어·채팅·제작 창. 언제 꺼져도 됨
```

- **실행 서버**는 가장 안정해야 하므로 코드를 최소로 두고 거의 바꾸지 않는다. Electron이어야 한다(트레이·`globalShortcut`이 Electron 기능).
- **작업실**은 자주 바뀌고 무거운 제작·채팅을 맡는다. 죽어도 돌고 있는 앱은 멈추지 않는다.
- **엔진 지기**는 작업실이 다시 켜지거나 업데이트돼도 진행 중인 개발 대화를 붙들고, 못 받은 출력부터 이어 준다(스튜디오 ADR 023).
- 프로세스끼리는 로컬 유닉스 소켓과 규격 봉투로만 말한다(v1 `popupServer`와 같은 방식).

### 5.3 고장별 복구

| 고장 | 누가 되살리나 | 어떻게 |
|---|---|---|
| 앱 하나가 죽음 | 실행 서버 | 1초 → 5초 → 30초 뒤 재시작. 10분 안에 5번이면 그 앱만 끄고 알림, 로그를 그 앱의 채팅 스레드에 붙인다 **[시작값]**. 이후 자가 유지보수([11절](#11-로그와-자가-유지보수))로 이어진다 |
| 앱이 멈춤/폭주 | 실행 서버 | 상주형 앱은 생존 신호를 보낸다. CPU 80% 이상 2분 지속이면 강제 종료 후 위 규칙 **[시작값]** |
| 실행 서버가 죽음 | launchd | 다시 띄우면 "켜져 있어야 할 앱 목록"으로 복원. 남은 앱 프로세스는 잠금 파일로 찾아 정리한 뒤 띄워, 같은 앱이 두 번 돌지 않게 한다 |
| 실행 서버가 켜자마자 3번 연속 죽음 | 실행 서버 | 안전 모드: 모든 앱을 끈 채로 뜨고, 마지막에 켜던 앱을 원인 후보로 표시. 정상 종료 코드로 끝내 launchd의 무한 재시작을 끊는다(스튜디오 `launchd.ts`) |
| 작업실이 죽음 | 사용자 | 앱 영향 없음. 메뉴바에서 다시 연다. 스레드는 추가 전용 기록이라 사라지지 않는다 |
| claude/codex가 죽음 | 대화 모듈 | 세션 번호로 `--resume` |
| 앱 수정본이 깨짐 | 보관소 | 새 버전이 켜진 뒤 10분 안에 반복해서 죽으면 이전 버전으로 자동 복귀 **[시작값]** |
| HackMac 자체 업데이트 | launchd + 실행 서버 | 실행 서버는 재시작 후 복원 경로. 엔진 지기는 도는 엔진이 없을 때만 교체 |
| 정전·강제 종료 | 모든 상태 파일 | 임시 파일 → 디스크 확정 → 바꿔 끼우기. 깨진 파일은 덮기 전에 사본, 주기 스냅샷(스튜디오 `durable.ts`) |

## 6. 엔진과 계정

### 6.1 엔진 선택 [결정]

- 로그인 감지: `claude auth status --json`, `codex login status`.
- 0개 → 로그인 화면. 1개 → 묻지 않고 그걸 쓴다. 2개 → 한 번 묻고 기본 엔진으로 저장, 설정에서 바꿀 수 있다.
- 로그인은 `claude auth login --claudeai`(브라우저가 준 코드를 화면에서 받아 CLI에 넣는다), `codex login`(브라우저 + localhost:1455 콜백). `--device-auth`는 쓰지 않는다: 사용자가 ChatGPT 설정에서 미리 켜야 한다. HackMac은 토큰을 읽지도 저장하지도 않는다. 저장된 엔진이 로그아웃되면 남은 쪽을 쓰고 알린다. 구현: `modules/account/`.
- 엔진 실행(`modules/conversation/`, 공통 인터페이스 하나 + 어댑터 둘):
  - Claude: `claude -p --input-format stream-json --output-format stream-json`을 상주시키고 글을 한 줄씩 넣는다(VS Code 확장과 같은 방식). `--permission-mode dontAsk --strict-mcp-config`. 중단은 stream-json `control_request{subtype:interrupt}`(실제 2.1.318에서 프로세스를 안 죽이고 멈춤 확인).
  - Codex: `codex app-server --listen stdio://` JSON-RPC. thread는 `approvalPolicy:never`, `sandbox:workspace-write`. 오는 승인 요청은 전부 거절로 자동 응답한다(안 하면 턴이 멈춘다). 중단은 `turn/interrupt`.
  - 일하는 중 보낸 글은 어댑터가 줄 세웠다가 턴이 끝나면 보낸다(Claude는 진행 중 글이 그 턴에 합쳐지는지 결과만 보고는 알 수 없었다, 스튜디오 2026-11-02 실측).
  - 실제 CLI 시험: `HACKMAC_REAL_ENGINES=1 npx vitest run modules/conversation/real.test.ts`(짧은 답·세션 이어 열기·중단, 두 회사 모두 통과 2026-11-06).
- 채팅 화면은 직접 만든다.

### 6.2 계정 전환

- 같은 회사 계정끼리는 자동 전환. 회사당 최대 3계정. 주간 사용률 구간(50·70·90%)을 비교해 더 여유 있는 계정으로 넘기고, 한도에 걸리면 아직 안 걸린 계정으로 넘긴다(스튜디오 `usage.ts`, `switcher.ts`).
- **대화가 진행 중일 때** 계정을 바꾸면 `--resume`이 자기 설정 폴더 안의 세션만 찾으므로 세션 기록을 새 계정 폴더로 복사한다. 대화가 끝나 기억 압축([12.2](#122-기억-압축))이 된 뒤에는 새 세션을 열므로 복사가 필요 없다.
- 다른 회사로는 진행 중인 개발 대화에서 넘기지 않는다(Claude 세션을 Codex에서 이어 열 수 없다). 새 스레드, 압축 뒤 다시 여는 스레드, 앱 실행 중 AI 호출에서만 넘기고, 진행 중인 대화에서는 사용자에게 묻는다.

### 6.3 앱 실행 중의 AI [결정]

- 앱이 AI를 쓸 때는 사용자의 로컬 엔진(같은 계정)으로 돈다.
- 앱은 `claude`를 직접 부르지 않고 **"AI 호출" 능력**을 부른다. 그래서 Claude 사용자가 만든 앱도 Codex만 쓰는 사람에게서 돈다.
- 주의: 백그라운드 앱의 AI 호출은 사용자가 코딩에 쓸 구독 한도를 같이 쓴다. 화면에 앱별 사용량을 보여 줘야 한다.

### 6.4 자식 프로세스 환경 [결정]

- Finder에서 연 앱은 터미널 PATH를 못 받는다. CLI는 PATH와 고정 설치 위치(`~/.local/bin`, `/opt/homebrew/bin`, nvm, volta 등)를 함께 뒤져 찾는다(스튜디오 `resolveBin`).
- `ANTHROPIC_API_KEY`, `OPENAI_API_KEY` 같은 변수가 자식 CLI에 닿으면 구독이 아니라 종량제로 조용히 과금된다. 매번 뗀다(스튜디오 `cleanEnv`).

## 7. 제작 과정

### 7.1 단계 [결정]

```
① 요구 정리 → ② 가능성 평가 → ③ 개발 → ④ 자체 검증 → ⑤ 사용자 확인 → ⑥ 완료
                    │                         │ 실패
                    ▼                         ▼
                 불가 설명  ◀─ 불가 ─ ⑦ 재조사 ─ 다른 방법 있음 → ③
```

- **① 요구 정리**: grill with docs 스킬로 채팅을 주고받아 요구사항을 명확히 한다. 결과는 번호 붙은 요구사항 목록이고, 이 목록이 진행 화면의 체크리스트가 된다.
- **⑤ 사용자 확인**: 권한 승인처럼 자동화로 넘을 수 없는 것만 사용자에게 부탁한다.

### 7.2 가능성 평가

- **만드는 에이전트가 아닌 별도 평가 역할이 한다.** 만드는 쪽은 "될 것 같다"로 기운다. 두 회사 계정이 모두 있으면 다른 회사 모델에게 맡긴다.
- 평가 항목: HackMac 능력 목록에 있는가 · macOS가 허용하는가([apple-app-data-access-guide.md](apple-app-data-access-guide.md) 체크리스트) · 외부 조건(데이터 출처, 유료 API 키, 호출 제한) · 필요한 권한.
- 판정: **가능 / 조건부 가능 / 불가능.** 실제 요청은 대부분 조건부다. 예: 주가 앱은 "15분 지연 시세면 바로 가능, 실시간은 유료 API 키 필요". 조건은 개발 전에 사용자가 확인한다.

### 7.3 "무조건 되게"의 정의 [결정]

- 사용자가 입력하면 에이전트가 스스로 테스트해서 되게 만든다.
- 보장하는 것은 **"검증을 통과한 것만 사용자에게 넘긴다"**이다. 능력 밖의 요청은 깨진 앱 대신 "못 한다"로 끝난다.
- 자동 테스트로 못 넘는 두 지점: 합성 키 입력은 `globalShortcut`까지 닿지 않고, 권한 승인 창은 사람이 눌러야 한다. 그래서 검증은 단축키 대신 스크립트를 직접 실행하고, 팝업 응답은 v1 E2E처럼 자동으로 채운다([e2e.md](e2e.md)). 권한 승인만 사용자에게 한 번 부탁한다.
- ④ 자체 검증에는 이식성 검사가 포함된다([9.4](#94-검증-게이트)).

### 7.4 불가능 판정과 메시지

- ④에서 실패하면: 같은 방법으로 3번 고치고, 안 되면 다른 방법으로 바꾼다. 방법 2개까지 써도 안 되면 ⑦ 재조사 **[시작값]**.
- ⑦ 재조사는 새 맥락의 다른 에이전트가 실패 기록을 넘겨받아 "정말 안 되는가"를 다시 판정한다.
- **"불가능" 판정에는 근거 2개 이상(실제 시도 기록 + 문서 출처)이 필요하다.** 없으면 판정을 낼 수 없다.
- 불가능의 이유 넷(이유에 따라 사용자가 할 수 있는 일이 다르다):
  - macOS가 막음: 어떤 앱도 못 한다.
  - HackMac에 아직 그 능력이 없음: 업데이트되면 된다.
  - 외부 조건: 유료 키, 계정, 데이터 출처가 있으면 된다.
  - 원인을 못 찾음: 모른다고 말한다.
- **실패 기록의 형식 [결정].** 유형(위 넷 중 하나) · 근거(시도 기록, 문서 출처) · "어떤 능력이 있었으면 됐나" 한 줄 · 확인한 macOS 버전. 유형은 틀릴 수 있으므로 근거 없는 판정은 기록만 하고 판정으로 세지 않는다. 이 기록을 어디에 쓸지는 이 문서에서 정하지 않는다.
- 채팅 메시지 형식: 결론 한 줄 → 쉬운 이유 1~2문장 → 대신 할 수 있는 것 → 접힌 기술 근거.

> **실시간 주가는 지금 만들 수 없어요.**
> 무료로 실시간 시세를 주는 곳이 없어서예요. 실시간 데이터는 증권 데이터 회사가 유료로만 제공해요.
> **대신 할 수 있는 것:** 15분 늦은 시세로 지금 바로 만들 수 있어요. 유료 API 키가 있으면 실시간으로 바꿀 수 있어요.
> ▸ 자세히 보기 (시도한 방법 2개, 확인한 출처)

## 8. 진행 현황 화면

### 8.1 원칙

- 진행 상태는 에이전트의 글에서 추측하지 않는다. 에이전트가 단계·요구사항 번호·상태를 **구조화된 이벤트**로 보내고, 화면은 그것만 그린다.
- 남은 시간 예측은 보여 주지 않는다. 경과 시간과 현재 단계를 보여 준다.
- 접수와 상태 응답은 1초 안에 코드가 낸다(스튜디오 원칙).
- 여러 앱을 동시에 만들 수 있으므로 메뉴바와 홈은 목록이다.

### 8.2 메뉴바

```
[아이콘 상태]  만드는 중 ◐ · 확인 필요 ● · 완료 ✓ · 불가 ✕

 ┌─────────────────────────────────┐
 │ 주가 표시    ③ 개발 · 6분        │
 │ ████████░░░░  요구사항 3/5      │
 │ 메일 요약    ⑤ 확인 필요 ●  [열기]│
 └─────────────────────────────────┘
```

- **가장 중요한 상태는 "확인 필요".** 권한 승인이나 조건 확인을 기다리는 동안 개발이 멈춘다. 아이콘에 점을 찍고 알림을 띄운다.
- 알림은 확인 필요 · 완료 · 불가 판정 때만.

### 8.3 HackMac 안 (채팅 스레드 화면)

```
 ①──②──●③──④──⑤──⑥     개발 중 · 6분
 지금: 주가 데이터를 받아오는 부분을 시험하는 중

 요구사항                       상태
 ✓ 메뉴바에 종목 3개 표시        시험 통과
 ✓ 1분마다 갱신                  시험 통과
 ◐ 종목 추가/삭제                만드는 중
 ○ 등락에 따라 색 바꾸기          대기
 ○ 장 마감 시 표시                대기
 ▸ 자세한 기록
```

- 요구사항 체크리스트가 핵심이다. ①의 항목이 그대로 줄이 되고, 각 줄이 "시험 통과"까지 간다.
- "지금" 줄은 쉬운 말 한 줄. 도구 이름("Bash 실행" 등)은 접힌 "자세한 기록"에만 둔다.
- 홈의 앱 카드에도 같은 진행 막대를 작게 보여 준다.

### 8.4 화면 배치 [결정]

홈 → 앱 카드 → 한 단계 아래 상세. 상세는 **왼쪽 상태 영역 + 오른쪽 채팅**으로 고정이다. 채팅은 언제나 오른쪽에 있고 왼쪽만 바뀐다.

```
 개발 중                          완료 후
 ┌──────────────┬────────┐       ┌──────────────┬────────┐
 │ ①②●③④⑤⑥ 6분 │        │       │ 켜기 ●  v3    │        │
 │ 지금: ...     │  채팅   │  →    │ 설명·트리거   │  채팅   │
 │ ✓✓◐○○ 체크   │        │       │ 권한·사용량   │        │
 │ ▸ 자세한 기록 │        │       │ 로그·버전     │        │
 └──────────────┴────────┘       │ 내보내기·레시피│        │
                                 └──────────────┴────────┘
```

- 개발 중에는 왼쪽이 모니터링 대시보드(8.3), 완료되면 앱 상세(켜기/끄기, 설명, 트리거, 권한, AI 사용량, 로그, 버전, 내보내기, 레시피)로 바뀐다.
- "고쳐줘"를 치면 왼쪽이 다시 대시보드가 되지만 위에 "v3 돌아가는 중" 띠가 남는다. 설치된 버전은 계속 돌고([10.2](#102-앱-버전-관리)), 수정본이 검증을 통과하면 "v4 적용" 버튼이 뜬다.
- 자가 유지보수([11절](#11-로그와-자가-유지보수))의 자동 수정도 같은 자리에 같은 모양으로 나타난다.

## 9. 앱 패키지와 이식성

### 9.1 내보내기/설치하기 [결정]

- 내보내기: 앱 폴더를 파일 하나(`.hackapp`, 확장자는 임시)로 묶는다.
- 설치하기:
  1. 파일 구조와 체크섬 확인.
  2. 앱이 요구하는 능력과 버전이 이 HackMac에 있는지 확인. 없으면 "HackMac 업데이트가 필요합니다"와 부족한 항목을 보여 준다.
  3. 앱이 선언한 권한과 능력을 요약해 보여 주고 사용자가 확인.
  4. 설치. 켜는 것은 사용자가 따로 한다.

### 9.2 앱 선언(manifest)에 들어갈 것

스키마 초안은 다음 작업이다. 최소한 아래가 들어간다.

- 앱 ID(작성자 + 이름). 같은 ID를 다시 설치하면 업그레이드, 기존 데이터 유지.
- 이름과 설명(사용자에게 보이는 글).
- 트리거: 단축키 · 메뉴바 상주 · 스케줄 · 로그인 시 등.
- 요구 능력과 버전(예: `popup >= 1`).
- 필요한 macOS 권한(자동화 대상 앱, 손쉬운 사용, 전체 디스크 접근 등).
- 설정 항목과 비밀 항목의 구분.
- 앱 버전.
- 작성자 서명 칸(예약만, 1차에는 비움).

### 9.3 이식성 규칙 [결정]

제작 모듈이 지키고 테스트가 강제한다.

1. **경로는 상대경로만.** `/Users/<이름>` 같은 절대경로를 쓰지 않는다. 앱 폴더와 데이터 폴더는 `$HACKMAC_APP_DIR`, `$HACKMAC_DATA_DIR`로 받는다.
2. **패키지와 데이터를 분리한다.** 내보내기에는 코드·선언·자산만 들어간다. 설정값과 비밀값(API 키 등)은 빠지고 받는 쪽에서 새로 입력한다.
3. **권한은 따라가지 않는다.** 선언만 따라가고, 받는 사람의 맥이 자기 승인 창을 띄운다.
4. **환경을 가정하지 않는다.** 믿을 수 있는 것은 macOS 기본 도구(zsh, osascript, curl 등)와 HackMac이 번들한 헬퍼뿐이다. 그 밖의 것은 선언에 적고, 없으면 설치 단계에서 막는다.
5. **능력 인터페이스에 버전을 붙인다.** 앱이 HackMac 업데이트보다 오래 살기 때문에, 능력 모듈을 교체할 때 옛 버전 호환이 계약이 된다.

### 9.4 검증 게이트

④ 자체 검증의 끝에서 앱을 내보내 빈 임시 폴더와 가짜 홈 디렉터리에 설치한 뒤 실제로 돌린다. "내 맥에서만 되는 앱"은 여기서 걸러진다.

### 9.5 받은 파일의 신뢰

받은 파일을 설치하는 것은 남의 코드를 실행하는 일이다. 선언 요약은 정직한 앱만 막아 줄 뿐, 선언보다 많은 일을 하는 스크립트는 못 막는다. 1차에는 서명 없이 "출처를 아는 사람의 파일만 설치하세요" 경고로 가고, 포맷에 서명 칸을 예약해 둔다.

## 10. 격리와 버전

### 10.1 개발 중 격리 [결정]

비전문가는 "이 명령 실행할까요?" 승인 창을 판단할 수 없어 에이전트는 승인 없이 돈다. 대신 에이전트가 작업 폴더 밖에 쓰지 못하게 막는다(스튜디오의 `sandbox-exec` 방식). 세부 범위(읽기 허용 범위, 네트워크)는 구현 때 정한다.

### 10.2 앱 버전 관리 [결정]

- 앱은 버전 폴더와 "현재 버전" 표시로 관리한다. 교체는 한 번에 바꿔 끼운다.
- 사용자는 "이전 버전으로"를 누를 수 있다. 자동 복귀 규칙은 [5.3](#53-고장별-복구).
- 개발 중인 수정본은 설치된 버전과 따로 두고, 검증을 통과해야 교체한다. 그래서 잘 돌던 앱이 수정 도중에 멈추지 않는다.
- 앱이 실패하면 로그가 그 앱의 채팅 스레드에 자동으로 붙는다.

## 11. 로그와 자가 유지보수

HackMac이 늘 떠 있으므로 앱 오류를 감시하다가, 고칠 수 있는 것이면 스스로 유지보수 팀을 불러 고치고 팝업으로 안내한다.

### 11.1 로그 세 층 [결정]

| 층 | 내용 | 형식 |
|---|---|---|
| 앱 실행 로그 | 실행마다 파일 하나, stdout/stderr 전부(v1 `exec-log.ts` 방식) | 자유 텍스트. 앱에 형식을 요구하지 않는다 |
| 사건 원장 | 죽음·재시작·자원 초과·권한 거부·검증 결과·자동 수정 | 추가 전용 JSONL(스튜디오 ledger 방식) |
| HackMac 자체 로그 | 실행 서버·엔진 지기·작업실 | 파일 |

### 11.2 감지와 분류

- 감시자는 실행 서버 안에 있다. 신호: 종료 코드, 반복 죽음, 자원 초과, 생존 신호 끊김, stderr 패턴(권한 거부·네트워크·파싱 실패), 스케줄 앱이 기대 결과 없이 끝남.
- **에이전트를 부르기 전에 코드가 먼저 분류한다.** 네트워크 끊김, 권한 거부, 외부 서비스 다운 같은 **외부 원인은 에이전트를 부르지 않고** 안내 팝업만 띄운다("미리알림 권한이 꺼져 있어요 → 설정 열기"). 사이트 구조 변경이나 환경 변화처럼 **코드로 풀 수 있는 원인만** 유지보수 팀을 부른다. 사용자 한도를 헛되이 쓰지 않기 위해서다.

### 11.3 유지보수 팀 [결정]

- 새 맥락의 별도 역할. 입력은 앱 패키지, 최근 로그, 사건 원장, 스레드의 압축 기억([12.2](#122-기억-압축)).
- 격리 폴더에서 수정본을 만들고 검증 게이트([9.4](#94-검증-게이트))를 통과해야 새 버전으로 저장된다.
- **자동 적용은 하지 않는다.** 팝업: 무슨 일인지 한 줄 → 원인 쉬운 말 → 고친 것 → [적용] [나중에] [자세히]. 설정에서 "자동 적용"을 켤 수 있고, 켜도 적용 후 알림은 간다.
- 고친 내용은 그 앱의 채팅 스레드에 메시지로 남는다("11월 6일 자동 수정: ...").
- 못 고치면 7.4의 재조사 경로로 가고, 앱은 끈 채로 스레드에 불가 메시지를 남긴다.

### 11.4 한도 보호

- 같은 앱은 하루 3번까지만 부른다 **[시작값]**.
- 조용한 시간(밤)에는 모아 뒀다가 아침에 한 번에 팝업한다.
- 사용자가 개발 중(작업실에서 엔진을 쓰는 중)일 때는 유지보수를 미룬다.

### 11.5 즉시 차단

심각 보안 문제로 판명된 앱은 팝업을 기다리지 않고 **앱을 바로 끄고** 알린다. 사용자 승인 없이 하는 유일한 동작이다.

## 12. 스레드 · 기억 · 레시피

### 12.1 스레드 = 앱 [결정]

- 스레드는 앱과 함께 태어나고 함께 산다. 안에는 원문 대화, 번호 붙은 요구사항 목록(살아 있는 문서), 결정 기록, 참고한 것([13.2](#132-참고-기록)), 엔진 세션 번호가 있다.
- 앱을 지우면 스레드는 보관함으로 간다(바로 지우지 않는다).
- 스레드는 내보낼 수 있는 형식이어야 한다(레시피의 재료).

### 12.2 기억 압축 [결정]

- 대화가 끝나고 30분 뒤 자동으로 압축한다 **[시작값]**. 바뀐 게 없으면 하지 않는다(한도 보호).
- 엔진에게 구조화된 출력을 강제해 **앱 기억 파일** 하나를 만든다: 요구사항 현재 상태 · 결정과 이유 · 사용자 환경 사실("회사 캘린더는 'Work'") · 시도했다 버린 방법 · 참고한 것 · 남은 숙제.
- **원문 대화는 지우지 않고** 접힌 기록으로 보관한다.
- 다음에 스레드를 열면 `--resume`이 아니라 **새 세션에 기억 파일과 최근 몇 턴만** 넣는다. 컨텍스트가 길어지지 않고, 계정·회사를 바꿔도 이어진다.

### 12.3 레시피

앱 파일 공유(그대로 설치)와 나란히 두는 두 번째 공유 방식. 받는 사람이 자기 환경에 맞게 다시 만든다.

- **레시피 제작 스킬**이 기억 파일에서 뽑는다. 출력은 텍스트 하나, 붙여넣기만으로 되는 프롬프트.
- 들어가는 것: 한 줄 목표 · 요구사항 목록 · 확정된 조건(예: "15분 지연 시세") · **환경 전제를 빈칸으로**("종목: ___", "캘린더 이름: ___") · 알려진 함정 · 참고 블록([13.3](#133-레시피의-참고-블록)).
- 빠지는 것: 개인 정보, 비밀값, 코드. 보내는 사람이 보내기 전에 빈칸과 참고 블록을 확인한다(참고 블록은 접어서 보여 준다).
- 받는 쪽: [앱 만들기] → 레시피 붙여넣기 → ① 요구 정리가 "빈칸만 채우는" 짧은 모드로 돌고 나머지 과정은 같다.

## 13. 오픈소스

### 13.1 원칙 [결정]: 앱은 참고만, 의존은 플랫폼이

- **참고**: 에이전트가 저장소를 읽고 방식을 빌려 스크립트로 다시 쓴다. 앱 안에 패키지가 남지 않는다.
- **의존**(앱이 돌 때 그 패키지가 필요한 것)은 **앱에 두지 않는다.** 라이브러리가 필요한 일(PDF 파싱, 이미지 처리, OAuth 등)은 우리가 능력으로 만들고, 그 안에서 오픈소스를 쓴다. 선정·고정·보안 공지 확인·교체는 우리가 릴리스 때 한다. 사용자 맥에서 패키지를 점검하지 않는다.
- 이유: 앱이 패키지를 동봉하면 이식성·서명·런타임·보안 공지·라이선스 문제가 전부 앱 단위로 따라온다. 4.4의 "앱은 능력의 조합과 스크립트만"을 지킨다.
- 비용: 에이전트가 라이브러리를 스크립트로 다시 쓰다 틀릴 수 있고(검증 게이트가 잡는다), 능력이 없어 못 만드는 경우가 는다(실패 기록으로 남는다).
- 참고의 규칙: MIT·Apache·BSD만 베낄 수 있고 표기를 남긴다. GPL류는 읽기만 한다. 베끼는 양에 상한을 둔다 **[시작값]**. 개발 중 에이전트가 GitHub를 읽어야 하므로 격리([10.1](#101-개발-중-격리))에서 네트워크 읽기는 허용한다.
- LLM 활용 오픈소스는 가치가 대부분 프롬프트와 흐름이다. 흐름을 빌려 "AI 호출" 능력 위에 다시 쓴다. OpenAI·Anthropic API를 직접 부르는 코드가 남으면 검증 게이트가 막는다(6.3과 충돌).

### 13.2 참고 기록

에이전트가 참고한 순간 기억 파일의 "참고한 것"에 남긴다: 저장소 주소 · **커밋 해시** · 파일/함수 위치 · 빌린 것 한 줄 · 라이선스 · 왜 골랐는지(대안 중 이유).

### 13.3 레시피의 참고 블록

> 참고: github.com/x/y @ a1b2c3 · `src/fetch.ts`의 `withRetry`
> 빌린 것: 429 응답일 때 지수 간격으로 3번 다시 요청하는 방식
> 이유: 이 사이트가 자주 429를 돌려줌. 다른 후보 2개는 보관된 저장소라 뺌
> 라이선스: MIT (표기 필요)

- 커밋을 고정하는 이유: 받는 쪽이 보낸 사람이 본 것과 같은 코드를 보게.
- 저장소가 사라졌으면 "빌린 것 한 줄"로 다른 참고를 찾거나 설명만으로 다시 쓴다. 이때 ① 요구 정리에서 "참고 자료 하나가 없어져 다른 방식으로 만듭니다"라고 알린다.
- 코드 자체는 넣지 않는다. 프롬프트와 흐름이 핵심인 경우만 흐름 요약(3~5줄)을 넣는다.
- 받는 쪽 에이전트는 참고 블록을 먼저 읽고 그다음 요구사항을 채운다. 자기 방식으로 먼저 만들었다가 나중에 참고를 보는 건 막는다.
