# Reminders/Calendar/Notes 데이터 접근 가이드

새 서비스 스크립트가 Reminders·Calendar·Notes 같은 Apple 기본 앱에서 제목·완료 여부·마감일 같은 기본 필드를
**넘어서는** 데이터(첨부파일, 공유 시트로 붙인 리치 링크, 폴더/스마트리스트 구조 등)를 읽어야 할 때 먼저 읽는다.
`gtd-reminders`의 기존 스크립트(01~07)처럼 이름/완료 여부/마감일/메모 텍스트만 다루는 스크립트는 이미 검증된
패턴이니 이 문서와 무관하다 — 그대로 따라 하면 된다.

이 문서는 미리알림의 "링크 카드"(공유 시트로 붙인 리치 링크 첨부)를 스크립트로 뽑아내려던 실제 시행착오에서
나왔다. 같은 원인 — **공개 API가 노출하지 않는 데이터를 공개 API로 찾으려 한 것** — 가 데이터 형식 오해 →
API 한계 → 성능 문제 → 툴체인 문제 → 권한 문제 순서로 층층이 다른 증상처럼 보였고, 그래서 한 번에 못 잡고
여러 번 다시 짰다. 아래 체크리스트를 스크립트 작성 **전에** 먼저 돌렸다면 대부분 한두 번의 실행으로 좁혀졌을
문제였다.

## 1. "링크"는 하나의 데이터가 아니다

Reminders 화면에 보이는 "링크"에는 서로 다른 저장 위치와 접근 경로를 가진 최소 세 종류가 있다. 하나로 뭉뚱그려
접근하면 나머지 두 개는 항상 0개로 보인다.

| 종류 | 실제 위치 | AppleScript로 접근 | EventKit(공개 API)로 접근 |
|---|---|---|---|
| 제목/메모 안의 일반 텍스트 URL | `body`(메모) 문자열 안 | 됨 — 문자열에서 정규식으로 뽑아야 함 | 됨 (`notes` 필드) |
| EventKit의 공개 `url` 속성 | 리마인더 자체의 URL 필드 | 됨 (`Reminders.app`의 사용자가 별도로 채워야 함) | 됨 (`EKReminder.url`) |
| 공유 시트로 붙인 "리치 링크" 첨부(카드 프리뷰) | 로컬 SQLite 저장소의 첨부 데이터 | **안 됨** — 공개 프로퍼티 없음 | **안 됨** — 공개 프로퍼티 없음 |

리치 링크 카드는 사용자가 Safari 등에서 공유 시트로 "미리알림에 추가"할 때 생기는 첨부(attachment)이지, 메모
텍스트도 아니고 EventKit이 노출하는 `url` 속성도 아니다. AppleScript와 EventKit 둘 다 기본 필드에는 적합하지만
첨부·리치 링크 같은 최신 기능은 완전히 노출하지 않는다.

## 2. 접근 방법별 능력 경계

| 방법 | 볼 수 있는 것 | 못 보는 것 | 필요 권한 |
|---|---|---|---|
| AppleScript(`osascript`, `tell application "Reminders"`) | 이름, 메모, 완료 여부, 마감일, 우선순위, 목록 구조 | 리치 링크 첨부, 폴더 안에 중첩된 목록을 항상 완전히 포함하지는 않음 | 자동화(Automation) 권한 — [환경에서 겪은 것들](../CLAUDE.md) 참고 |
| EventKit(Swift/Objective-C 헬퍼) | AppleScript와 대체로 동일 + 비동기 대량 조회에 유리 | 첨부 메타데이터(공개 API가 반환하지 않음) | 미리알림 접근(Reminders) 권한 |
| 로컬 SQLite 저장소 직접 읽기 (읽기 전용) | 첨부 데이터를 포함한 원시 레코드 전부 | 공식 지원 스키마가 아님 — OS 업데이트로 스키마가 바뀌면 깨질 수 있다 | **전체 디스크 접근(Full Disk Access)** — 저장소가 개인정보 보호 영역에 있어 이 권한 없이는 파일이 아예 안 보인다 |

리치 링크처럼 공개 API 밖의 데이터가 필요하다는 게 확정되면 SQLite 직접 읽기까지 내려가야 하고, 그 경우
Full Disk Access 요구는 피할 수 없는 구조적 제약이다 — 버그가 아니라 macOS의 개인정보 보호 설계다. 이 권한이
필요한 서비스는 스토어 카피(`usage`)에 "최초 실행 시 시스템 설정 → 개인정보 보호 및 보안 → 전체 디스크
접근에서 허용해야 한다"는 안내를 반드시 포함시킨다.

## 3. 새 스크립트를 작성하기 전에: 사전 진단 체크리스트

기본 필드를 넘어서는 데이터를 다루는 스크립트를 새로 만들 때는, 전체 기능을 구현하기 전에 아래 순서로 먼저
확인한다. 순서를 지키는 이유는 앞 단계에서 막히면 뒤 단계는 시도할 필요조차 없기 때문이다.

1. **zsh 예약 변수·실행 환경 확인** — 아래 4번 항목의 변수명 함정을 피했는지 먼저 점검한다.
2. **AppleScript/EventKit으로 목록명과 미완료 항목 수만 우선 출력** — 전체 기능을 짜기 전에 "목록이 몇 개
   보이는가, 그 안에 항목이 몇 개인가"부터 `echo`로 확인한다. 폴더 안에 중첩된 목록이 빠져 있지 않은지 이
   단계에서 걸러진다.
3. **메모 속 텍스트 URL, 공개 `url` 속성, 리치 링크(있다면)를 각각 별도로 집계** — 이 셋을 하나의 카운트로
   합치지 않는다. 하나가 0이어도 나머지가 0이 아닐 수 있다.
4. **리치 링크가 필요하다고 판단되면, 그 시점에 SQLite 저장소 경로 존재 여부와 읽기 권한을 먼저 확인** —
   실제 파싱 로직을 짜기 전에 파일을 열 수 있는지부터 본다.
5. **전체 디스크 접근이 없으면 그 자리에서 바로 사용자에게 설정 화면 경로를 안내하고 종료** — 권한 없이 계속
   시도하며 로그만 쌓지 않는다.
6. **위 네 가지가 다 확인된 뒤에야** 실제 데이터 수집·가공(Markdown 생성 등) 로직을 짠다.

## 4. zsh 스크립팅에서 걸리는 함정

- **`status`는 zsh 예약 파라미터다.** 일반 변수처럼 `status=1`을 쓰면 `read-only variable: status` 에러가
  난다. 결과값을 담는 변수 이름에 zsh 특수 파라미터(`status`, `path`, `PATH`, `PWD`, `HOME`, `IFS`, `TTY`
  등)를 쓰지 말고 `exit_status`, `result_code`처럼 접두어를 붙인다.
- **이 앱은 스크립트를 30초(`electron/runner.ts`의 `TIMEOUT_MS`)가 지나면 강제 종료(`SIGTERM`)한다.** 항목별로
  Apple Event를 하나씩 날리는 반복문(예: 리마인더 하나하나의 속성을 개별 조회)은 목록이 커지면 이 타임아웃에
  걸린다 — [환경에서 겪은 것들](../CLAUDE.md)의 `whose` 필터/벌크 읽기 관련 항목을 참고해 벌크 읽기로 바꾼다.

## 5. 로깅 설계 원칙 — "0개"의 세 가지 의미를 구분한다

이 앱은 모든 스크립트 실행을 `~/Library/Logs/<앱 이름>/<날짜>/`에 자동으로 파일 로그로 남긴다
(`electron/exec-log.ts`) — 스크립트가 stdout/stderr로 출력하는 모든 줄이 타임스탬프와 함께 그대로 저장되고,
`SIGTERM`으로 강제 종료됐을 때도 `중단 신호를 받았습니다: SIGTERM` 줄이 남는다. 즉 **별도 로그 파일을 만들
필요 없이 스크립트 안에서 `echo`/`display notification`으로 충분히 출력하기만 하면 진단이 가능하다.** (렌더러로
돌아가는 `stdout`/`stderr` 문자열은 4000자로 잘리지만, 로그 파일 자체는 잘리지 않는다.)

새 데이터 수집 스크립트를 짤 때는 첫 버전부터 아래를 반드시 출력한다. "링크가 0개로 나왔다"는 결과 하나만
남기면, 그게 정말 0개인지 API가 애초에 지원하지 않는지 권한이 없어서인지 구분할 수 없다 — 이 구분 실패가
실제 시행착오에서 가장 큰 시간을 잡아먹은 원인이었다.

- 전체 목록 수와 목록명
- 목록별 전체/미완료 항목 수
- 메모 속 텍스트 URL 개수 / 공개 `url` 속성 개수 / 리치 링크 개수를 **따로따로**
- 폴더 내부 목록까지 포함해서 순회했는지 여부
- (SQLite를 다루는 경우) 데이터베이스 경로 존재 여부와 읽기 권한 여부

그리고 다음을 하지 않는다:

- JXA/AppleScript 예외를 빈 `catch`/`on error`로 조용히 삼키기 — "속성이 없음"과 "접근 실패"를 구분할 수
  없게 된다. 최소한 `errText`/`errNum`을 로그에 남긴다.
- "데이터 없음", "API가 지원 안 함", "권한 없음"을 전부 같은 "0개"로 표시하기.

## 관련 문서

- macOS 자동화 권한 승인 창 블로킹, `whose` 필터 성능, 다이얼로그 포커스 등 AppleScript/osascript 자체의
  함정은 [CLAUDE.md의 "환경에서 겪은 것들"](../CLAUDE.md)에 정리돼 있다 — 이 문서와 같이 읽는다.
- 이렇게 검증된 스크립트를 서비스로 승격하는 절차는 [docs/playbook-graduation.md](playbook-graduation.md) 참고.
